## Contract and implementation

- POST `/api/employees` assigns a server-generated number. A new isolated database starts at `100000`; gaps are allowed.
- Create and update request models no longer expose an editable employee number. Supplying `employeeNumber` returns HTTP 400, including unchanged or null values; field matching is case-insensitive.
- Employee detail/list responses retain the existing number and GUID fields. Profile updates, employment changes and separate D13 account provisioning retain the employee identity.
- The frontend removes number entry from registration and profile editing, displays the permanent number read-only, and navigates to the created employee profile with the actual assigned number in its success message. Existing V3 components and layout are retained.
- Existing capability filters, Identity, CSRF, account activation and audit mechanisms are reused unchanged. Registration still creates the employee, child records and initial employment in one transaction; it does not provision a user account.

## Database design

Migration: `20261009064219_AddPermanentEmployeeNumbering`.

Additions:

1. `dbo.EmployeeNumberSequence`: noncycling bigint sequence, minimum/start 100000, maximum 9223372036854775806.
2. `EmployeeNumberReservations`: number primary key, unique EmployeeId snapshot, UTC reservation/assignment/retirement timestamps and state check constraint. EmployeeId deliberately has no foreign key, so historical reservations survive deletion.
3. `dbo.ReserveEmployeeNumber`: consumes the sequence and commits its reservation using a separate, non-enlisted connection. It rejects execution inside an existing SQL transaction.
4. `TR_Employees_PermanentIdentity`: rejects number/GUID changes and unreserved, assigned or retired insertion; records first assignment and retirement.
5. `TR_EmployeeNumberReservations_Permanent`: prohibits deletion/rebinding and permits only first assignment or retirement transitions.

The existing unique Employees.EmployeeNumber index remains. EF SQL OUTPUT is disabled for trigger-backed employee/ledger tables. Runtime allocation never calculates MAX + 1. The migration performs a one-time numeric collision preflight, advancing beyond existing numeric identifiers without changing their original formatting. Capacity exhaustion aborts the migration transaction.

Reservation is the sole intentionally independent write. A registration failure rolls back employee/employment/audit writes while preserving the reserved number as a permanent gap. Sequence gaps from cancellations or SQL caching are also acceptable. Allocated numbers and GUID bindings cannot be recycled through ordinary SQL or the API. Schema-owning administrators can alter database protections; this is not a claim of protection against privileged schema tampering.

## Compatibility, deployment and rollback

- Existing employees are backfilled into the ledger; their numbers, GUIDs, active state, relationships and historical records are not renumbered or rewritten.
- New numbering protection applies to all numbers present at migration and all subsequent reservations. Numbers deleted before migration cannot be reconstructed from absent records; any known historic deletions should be supplied for review before deployment.
- Old clients that submit employeeNumber must remove it. Direct employee imports/fixtures must reserve a number first. This is an intentional create/update contract change; read contracts remain compatible.
- Apply during a coordinated maintenance window with employee writes stopped, after reviewing a backup and the generated focused SQL. Deploy the matching backend/frontend together; the updated backend requires the new schema for registration. The currently running Development API remains on its previous schema-compatible binary.
- No automatic downgrade: Down throws 51006 rather than erasing lifetime reservations. A reviewed recovery plan must retain the ledger and sequence high-water history. Restoring an older backup without preserving numbers allocated afterward can violate the never-reuse guarantee.
- Focused idempotent review SQL: `.artifacts/F51A-EmployeeNumbering.sql`. It is generated, not executed against SIAMIS.
