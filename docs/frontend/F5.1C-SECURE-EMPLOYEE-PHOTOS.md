## Implementation

- Dedicated private photo revisions and access rules, separate from confidential HR documents. Employee numbers, employee GUIDs, employment history and account provisioning remain unchanged.
- Employee Directory and Employee 360 retrieve current photographs through the existing authenticated API client. They use revocable in-memory blob URLs, loading indicators and initials fallback. No public/storage locator is used as an image source.
- Employee 360 exposes a compact shared Dialog for selecting, previewing, uploading, replacing and confirming removal. Required capabilities, submission protection, dirty-close protection, keyboard focus restoration and useful validation errors are retained.
- Registration remains atomic employee + initial employment creation. A photograph is an independent operation after successful registration, from Employee 360; registration/edit guidance explains this. No staged photograph or draft employee workflow is introduced.
- Legacy `ProfilePhoto` database values are preserved, but are no longer exposed as URLs in list/detail DTOs. The existing nullable response field remains present as null. Supplying a non-null legacy locator in profile writes is rejected; the frontend omits that field. Development has zero legacy locators, so no existing photographs require conversion there. Other deployments must inspect any legacy locators before rollout; automatic import is deliberately absent.

## API and authorization

| Operation                                   | Endpoint                                                                             | Capability             |
| ------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------- |
| Current metadata or explicit no-photo state | `GET /api/employees/{employeeId}/photo`                                              | Employee.Read          |
| Current private binary                      | `GET /api/employees/{employeeId}/photo/content?version={revisionId}`                 | Employee.Read          |
| Upload/replace                              | `PUT /api/employees/{employeeId}/photo` multipart `file`, optional `expectedVersion` | Employee.Manage + CSRF |
| Remove                                      | `DELETE /api/employees/{employeeId}/photo` JSON `expectedVersion`                    | Employee.Manage + CSRF |

Metadata includes only revision ID, presence, dimensions, byte size and validated content type. Binary responses use no-store, nosniff and a restrictive CSP. A revision ID is scoped to its employee and must still be current; superseded/removed binaries return 404. The service repeats capability checks in addition to the existing HTTP authorization filter. SelfService alone grants no general photo access, including through a guessed employee/photo ID. SystemAdmin photo access does not grant HRDocuments access.

Statuses: 400 invalid image/dimensions/filename or missing CSRF; 401 unauthenticated; 403 insufficient capability; 404 missing employee/current photo; 409 stale version/concurrent command; 413 oversized content; 415 unsupported content; 503 unavailable storage/metadata or failed safe persistence.

## Image validation and storage

- Limit is 5 MiB (5,242,880 bytes), following the existing binary-size convention; decoded width and height each must be at most 4096 pixels.
- Accept only actual JPEG/PNG decoded content. Filename/MIME claims are not trusted. Read bytes with a bounded buffer, inspect dimensions before pixel allocation, and require a complete successful pixel decode. Also require complete JPEG termination and complete PNG chunk framing/checksums; animated PNGs are rejected as non-still photographs. Concurrent decoding is bounded to two buffers.
- SkiaSharp 4.151.2 and matching Linux native assets are the only new dependencies. A maintained actual image decoder is necessary; header-only document validation is insufficient. See [official package](https://www.nuget.org/packages/SkiaSharp/4.151.2) and [decoder API](https://learn.microsoft.com/en-us/dotnet/api/skiasharp.skcodec.getpixels?view=skiasharp-3.119).
- Reuse private-document storage mechanics through a separate `IEmployeePhotoStorage` instance/root. Keys and stored filenames are server-generated; original filenames are validated and never used to construct paths. Stored bytes carry SHA-256 and length verification before serving.
- Development default: private `App_Data/employee-photos`. Production has no default storage root and fails closed unless explicitly configured with `EmployeePhotos:Root`. Reject relative roots, web-root locations and overlap with confidential-document storage. Deployment must provision a private writable directory, restrict OS access and back up database metadata and private bytes together. Multi-instance deployments require a shared private storage root and consistent permissions.
- Original validated bytes are retained, without destructive conversion/resizing. Embedded EXIF metadata is therefore retained privately and can be present in authorized downloads. No EXIF stripping, image cropping UI, self-service photo management or historical binary retrieval is implemented.

## Consistency, auditing and retention

- Employee-first SQL locking and a Serializable transaction serialize commands. Every mutation compares the observed revision ID. A filtered unique index permits one current revision per employee; the current marker is an EF concurrency token.
- Metadata and an authenticated SecurityAuditEvent commit together. Upload, replacement and removal retain actor, UTC timestamp, operation and employee/revision identity. Original revision fields are immutable through EF; only retiring the current-head marker is permitted.
- Removal creates a current tombstone and restores initials. Replaced/removed binaries and their audit metadata are retained indefinitely in private storage for this milestone. They cannot be read through the current-photo endpoint. No automated purge is introduced. A time-based retention/purge policy requires a separately reviewed operational procedure; this implementation's indefinite retention should be reviewed before Production rollout.
- Failed writes roll back metadata/head/audit together and remove uncommitted bytes. If commit outcome is uncertain, a fresh database probe prevents deleting a committed binary. Failed cleanup or an unavailable reconciliation probe leaves a private orphan and logs a revision ID for operator reconciliation; it never exposes an uncommitted image as current. Operators must establish that a key is unreferenced before any approved orphan purge. No automatic reconciliation job is introduced.
