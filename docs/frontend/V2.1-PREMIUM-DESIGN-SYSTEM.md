## 2. Global product scope and preserved engine

This is the master foundation for the entire SIAMIS ecosystem: authentication and shell; school/campus; academic years/terms; admissions/CRM and enrollment; students and guardians; classes, subjects and teacher assignments; attendance and timetable; assessment, examinations and results; documents, welfare and calendar; HR and payroll; accounting/finance; professional development; communication; tasks/projects; analytics; and user/role/security administration.

Consistency standardizes quality and interaction language, **not page composition**. All existing backend contracts, authorization semantics, session flows, query behavior and business rules remain authoritative. No operational module or production-page redesign is implemented here.

## 3. Design philosophy

Use typography, alignment, useful density, surface contrast and subtle dividers before adding containers. Burgundy identifies primary interaction; gold adds restrained school identity. Plain aligned metrics and compact queues are preferred over repeated floating cards. Use local system fonts. No decorative charts, fabricated trends, gradients, glass effects, marketing headings or animation libraries.

## 6. Spacing and density

Use the existing 4px `--space-unit`, extended named steps 4, 8, 12, 16, 24, 32 and 48px. Page gutters use `clamp(16px, 3vw, 40px)`. Form rhythm retains 8px label/control and 6px control/helper/error gaps. Section spacing is 32px desktop/24px mobile; grouped primary content uses 24px desktop/16px mobile padding. Align related content rather than multiplying cards.

Default controls/touch targets are 44px minimum. The 36px compact-control token is reserved for a deliberate future desktop density option; no blanket shrinking occurs. Native table cells use 8px vertical/16px horizontal padding, with interactive rows sized by their accessible controls.

## 7. Surfaces, borders, radius and elevation

Canvas → unboxed page content → primary reading/working area → grouped secondary context → elevated interaction. Use restrained 4px control and 6px panel radius. Most content has no shadow. Borders define table/group boundaries; elevation is for dialogs, menus and contextual overlays. Avoid nested cards and independent floating surfaces for every fact.

## 8. Buttons and iconography

Existing Button variants remain: primary, secondary, outline, ghost/quiet, destructive and icon-only. Use one primary command for the current task; secondary/quiet for auxiliary actions. Preserve native disabled semantics and `aria-busy`/duplicate-submission prevention. Primary hover/active colors are explicit tokens, not opacity alone. Focus remains visible.

Use 16px action icons and 20px navigation/context icons when useful; 8px icon/label spacing and 44px icon-action targets. Icons supplement meaning; icon-only actions require accessible names. Do not place an icon beside every label.

## 9. Forms

Reuse Input, Textarea, Select, Checkbox, RadioGroup, Switch and FormField. Text/password/date use native input semantics where supported. Keep visible associated labels, required indicators and clear helper/error IDs. Forms group into sections; never rely on placeholders as labels.

Default, hover, blue focus, red invalid borders/pale error surface, filled, disabled and read-only states are distinct. Read-only styling applies to actual inputs/textareas, not every Radix select trigger. Preserve autocomplete, with scoped autofill text/surface treatment. Actual password-manager autofill was not reproducible in this verification.

Field validation belongs to the field; command/server errors belong to the form/section. Maintain entered values and avoid permanent oversized error space. Long workflows use full pages; short contextual forms may use dialogs. No authentication handlers were changed.

## 10. Status language

Neutral, info, success, warning and danger use readable text plus restrained tint and small-radius labels. Text conveys status without relying on color. Callers map domain states to presentation; Badge does not invent policy. Avoid saturated pills for every piece of metadata. Do not infer payroll effects, misconduct or approval from a visual intent.

## 11. Feedback and system states

SystemState distinguishes `empty`, `search`, `filtered`, `configuration`, `disconnected`, `permission` and `error`. It accepts explicit guidance and an optional **already authorized** action. Only error intent announces an alert automatically; static empty/configuration guidance does not claim failure.

Use Alert for contextual information/success/warnings, field-associated FormField errors for validation, and existing notification infrastructure for transient confirmations. A permission limitation is not no data; a missing configuration is not a failed request; an expired session requires the existing authentication path.

## 12. Loading and empty states

Use busy/disabled Button for a command, Spinner for concise inline progress, and structure-matching Skeletons for section/page content loading. Avoid a full-page spinner for a small section update. Keep expected dimensions stable and respect reduced motion.

Empty states should explain what belongs there and the appropriate next step. Search/filtered emptiness suggests adjusting terms/filters. Missing configuration suggests the prerequisite. Disconnection/unavailability never becomes an invented zero metric. Retain the old EmptyState API for compatibility; the new compact SystemState is the preferred operational pattern.

## 13. Enterprise tables

Retain semantic Table/Header/Row/Head/Cell wrappers, captions, column headers and real controls. Use identity plus concise metadata, textual status, aligned dates, right-aligned tabular numeric values, restrained actions, meaningful sorting (`aria-sort`), selected state and pagination. Static rows are not falsely clickable.

TableViewport provides a named focusable scrolling region and positions accessibility text within it. This prevents absolutely positioned hidden table labels/captions from causing page overflow. No large vertical borders, decorative stripes or oversized rows.

The showcase implements local specimen search/filter/reset, sort, selection and pagination. These are Development UI examples, never runtime school records or bulk domain actions.

## 14. Search and filters

FilterBar composes labeled search and frequent filters directly beside the data. Display active-filter count and clear/reset; reset pagination when filters/sort change. Mobile filters become readable full-width controls. Advanced filters may be disclosed where needed, but do not hide all frequent operations behind dialogs. Backend query contracts remain untouched.

## 15. Metrics, lists and queues

MetricStrip groups factual values in a definition list without a separate card for each value. Every metric requires context; unavailable values remain explicitly unavailable. Showcase counts describe its own local specimens/archetypes only.

QueueList combines title, metadata, optional meaningful status and optional action. Static entries have no click affordance. Applicable to admissions, leave, attendance review, documents, academic exceptions and tasks; no business rules reside in this primitive.

## 16. Page headers and record foundations

WorkspaceHeader composes context/breadcrumb, one compact h1, concise description and optional action slots. RecordSummary composes identity, metadata, status and contextual actions. Existing Tabs support caller-supplied accessible group labels. Related sections and timeline/history specimens demonstrate structure; no real student/employee record page was added.

## 17. Dialogs and confirmations

Retain Radix focus containment, Escape close and trigger-focus restoration. Dialog and AlertDialog titles/descriptions stay associated. Destructive confirmations initially focus Cancel and use an explicit contextual `confirmLabel` (default Confirm). Mobile overlays fit the viewport; regular dialogs have bounded scrollable content. No new confirmation workflow or business operation was introduced.

## 18. Responsive composition

Keep existing Tailwind breakpoints and production shell unchanged. The showcase uses a 1024px threshold for sidebar → horizontal section navigation and a 1340px threshold for side-by-side directory/queue → full-width directory with queue below. Under 640px, forms/feedback/record sections prioritize a single reading column; palette specimens remain two columns. These are showcase composition choices, not mandatory layouts for every module.

For tables, choose priority columns, contained horizontal scrolling, compact lists or secondary detail disclosure **per workflow**. Complex tables retain readable columns. Do not globally turn all rows into cards. This showcase demonstrates contained scrolling at 768/430/390px with no horizontal page scrolling.

## 19. Accessibility and motion

Semantic headings/forms/tables/lists, meaningful labels, keyboard navigation, clear focus, associated errors and non-color-only statuses remain required. Skip navigation is available. Dialog focus return and safe cancellation were verified. Table regions are keyboard reachable. Motion is short and functional; existing reduced-motion rules suppress unnecessary animation. No animation dependency was added.

### Interaction polish audit

- Shared feedback uses `--motion-fast: 120ms` and `--motion-ease: cubic-bezier(0.2, 0, 0, 1)` for color/border/background/opacity changes. The switch thumb uses the same timing for its existing positional state change. No layout dimensions are animated.
- Buttons, including pagination and queue icon actions, retain immediate commands, native disabled/loading semantics and visible focus. Disabled buttons no longer acquire variant hover feedback. Inputs/selects, checkbox/radio/switch and tabs share restrained state feedback. Read-only fields do not advertise editable hover feedback.
- Focus outlines appear immediately and are not faded or animated. Shared choice controls, tabs and menu items use the V2 blue focus role. Existing error and selected meanings remain distinct.
- Existing Radix dialog/confirmation/select/menu/popover/tooltip surfaces use a 100ms opacity-only opening reveal (`--motion-overlay`). Closing, focus return, navigation and commands have no animation delay; no scale, slide or bounce is introduced. Destructive confirmation keeps Cancel as the initial focus.
- Table hover/focus feedback applies only when a row contains an enabled control/link. Selected rows retain their selected surface while hovered/focused. Queue items remain static; feedback is on their actual action buttons. Metrics, panels and ordinary information have no hover movement or decoration.
- Existing loading/spinner and skeleton patterns remain. Under `prefers-reduced-motion: reduce`, transitions and animations are disabled entirely, including spinners/skeleton pulses, while textual/busy loading indicators remain available.
- Browser checks covered choice changes, select opening/selection, keyboard tabs, dialog Escape/focus return, safe confirmation cancellation, table selection and pagination. Menus/popovers were inspected at the shared implementation level; no new showcase composition was added. Reduced-motion CSS was inspected; OS preference switching was not performed.

## 21. Data honesty

No fake runtime metrics, trends, records, financial amounts, calendar events or grades. Operational visualizations require actual backend semantics. Unavailable data uses honest state presentation. Fictional Development specimens are clearly marked, save nothing and never enter operational routes. The production build excludes the showcase and its specimen data.

## 22. Authorization-aware UX

Capability-aware callers decide whether to render actions; backend authorization stays authoritative. Roles, titles and employment positions never establish UI permission. Distinguish denied capability, missing configuration, no records, disconnection and request failure. New primitives do not implement or bypass authorization.

## 23. Attendance / payroll meaning

Attendance records what happened; authorization determines whether permitted; payroll determines financial consequences. Future screens must separately represent raw evidence, expected schedule, exceptions, review, finalization and actual payroll outcome. Lateness/early departure do not imply automatic salary deduction. V2.1 adds no attendance or payroll behavior.

## 24. Deprecated patterns and compatibility effects

- Replace the old showcase's repeated generic card grids and blanket mobile table-card transformation with purposeful grouped surfaces and workflow-specific responsive strategies.
- Prefer compact textual status labels to rounded pills everywhere.
- Prefer WorkspaceHeader to marketing-sized page headings for new V2 operational work; existing production headers remain intact pending later phases.
- Prefer SystemState to large decorative/dashed empty boxes for compact workspaces. Legacy EmptyState and StatisticCard remain for current consumers, not as mandatory new templates.
- Replace hard-coded “Example views”/“Confirm example” wording inside reusable components with caller-aware labels.
- F3.5's rejected visual experiment remains preserved and is not the V2 auth reference. No login, HR or shell composition was redesigned.

Minor shared effects are intentional: control/button radius 4px, primary hover/active/focus styling, correct read-only select appearance, invalid field surfaces, 16px mobile editable controls, tighter table padding and compact status labels. Existing auth-scoped 48px fields/card/background and F4 integration remain; consumers inherit primitive styling, not a page redesign.
