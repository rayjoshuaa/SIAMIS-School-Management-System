## 1. Root cause

Previously, `POST /api/employees` had no request identity or durable replay record. The form's synchronous pending guard prevented immediate repeated clicks but could not protect network retries, lost responses or concurrent API requests. F5.1E's six identical valid requests therefore created six employees with different numbers. Matching people by name/contact details would incorrectly reject legitimate registrations and has not been added.

## 4. Backend architecture and lifecycle

`POST /api/employees` now requires a nonempty UUID in `Idempotency-Key`. Authentication, existing Employee.Manage authorization and CSRF filters run before the action can read a receipt. The service also requires the authenticated actor and Employee.Manage. The client cannot supply actor identity or operation scope.

The key is scoped by `(ActorUserId, Employee.Register.v1, RequestKey)`, enforced by the SQL primary key. A unique result-employee index prevents associating multiple completed receipts with the same employee. Actor/key identities must be nonempty; operation is fixed and binary-collated.

The canonical SHA-256 fingerprint uses validated typed input, stable property ordering, existing trimmed-string/null semantics, equivalent null/empty creation collections and normalized decimal representations. Collection order remains significant. Ignored extension fields do not affect the fingerprint; existing validation still rejects client-supplied employee numbers, initial status and photo locators. No personal matching rules are used. The submitted request and credentials are not persisted.

Inside the Serializable registration transaction, the service obtains a transaction-owned SQL application lock for the actor/operation/key with a **5-second maximum lock wait**. The database lock manager coordinates independent API instances. A completed-receipt lookup uses READCOMMITTEDLOCK under that application lock, avoiding unrelated missing-key range locks. Database uniqueness remains an independent safeguard.

For a new request, normal employee/initial employment/child validation and creation run. After saving, the response is mapped from tracked creation data plus individual reference rows **inside the transaction**; the completed receipt and its authenticated audit are saved before commit. Employee, initial employment, successful response receipt and audit therefore commit together. Only completed receipts are persisted: there is no durable Pending state to strand after a failure. Cancellation/SQL command timeouts and transaction disposal release locks; an uncertain outcome must be resolved by retrying the same key.

The original authorized registration response is stored as JSON because rereading a subsequently edited profile would not return the original result. It includes only the existing registration response fields and must retain restricted employee-database/backup access. There is no public receipt lookup/list API. Result IDs/numbers and scoped keys remain immutable; no cascading User/Employee foreign keys are introduced. Legitimate later deletion never erases a receipt or resurrects its employee during replay.

Audit integrity is preserved: new registration/receipt changes use the established authenticated actor mechanism; a successful replay creates no duplicate employee mutation/audit events. ResultEmployeeId is deliberately a historical result identity rather than a new operational employee-history dependency.

## 5. Replay, expiry and numbering

| Request                                         | Actual result                                              |
| ----------------------------------------------- | ---------------------------------------------------------- |
| First valid scoped key                          | 201; one employee, initial employment and receipt          |
| Equivalent committed replay within 30 days      | Original 201 body and employee Location; no new allocation |
| Same scoped key, different payload              | 409, code `idempotency_conflict`                           |
| Same key still locked after bounded wait        | 409, code `registration_in_progress`, Retry-After: 5       |
| Equivalent expired committed key                | 410, code `registration_key_expired`; never new creation   |
| Invalid/empty/missing key or validation failure | 400; no registration                                       |
| Anonymous / unauthorized / missing CSRF         | Existing 401 / 403 / 400 rejection before replay           |
| Different keys with equivalent personal details | Separate legitimate registrations                          |

Payload mismatch is checked before expiry, so a changed payload using an expired key remains a conflict. Both outcomes prohibit creation.

The 30-day window uses authoritative SQL UTC timestamps. Expiry does not delete or recycle keys. Permanent tombstones retain scoped key, hash and result identity. The SQL trigger permits only clearing an existing response after expiry; it blocks premature purge, response replacement, key/result/hash/time changes and deletion. No scheduled response-purge job is introduced; expired response cleanup requires controlled maintenance. Expired responses are not returned even if still physically retained.

Existing independent number reservation and sequence behavior is unchanged. Only the winning creation attempt calls the allocator; successful replay does not. Failed/uncommitted attempts may leave the explicitly approved permanent gaps. Committed/retired numbers cannot be reused. Down refuses removal of a nonempty receipt ledger; application rollback must preserve replay protection and reservations. Empty unused receipt schema can be dropped through the migration's guarded Down.

## 6. Frontend integration

The existing V3 registration form generates a cryptographically random UUID for a logical valid create submission. It retains key and payload through retries. The API client sends the key only for employee registration; CSRF acquisition, cookies and session-loss handling remain unchanged.

The synchronous submission guard and loading button prevent repeated clicks. During pending or uncertain outcomes, the field group is disabled while preserving the original section spacing and accessible controls. A timeout/network/server/in-progress result leaves the original details/key frozen and displays **Retry original submission**. That action sends the same original payload and key; it never silently sends edited details or starts a second registration. Conflict/expiry states clearly stop submission and direct the operator to review the directory. Definitive validation failure permits corrections; a changed logical payload gets a fresh key. A new intentional registration after success also gets a fresh key.

Successful first creation or replay navigates to Employee 360 with the existing generated-number success message. Account provisioning, initial status, immutable numbering and other lifecycle forms are preserved. Error normalization recognizes only the three allowlisted registration codes and still suppresses arbitrary server detail/stack traces.

Keys and frozen payloads are held only in the current editor's memory. Existing unsaved/pending navigation protections remain; closing/refreshing/abandoning the editor can lose its retry key and details. No automatic resubmission occurs, and no cross-tab/draft/browser persistence was added. A caller must retain its key to resolve an ambiguous result; manual fresh-key registration of the same person remains possible by design. This limitation is distinct from prohibited person matching.
