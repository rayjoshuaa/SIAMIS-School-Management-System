# SIAMIS V3.5 — Employee Directory and Employee 360

Status: **V3.5 PREMIUM EMPLOYEE DIRECTORY & EMPLOYEE 360 READY FOR PRODUCT-OWNER REVIEW**. Product-owner visual approval pending. No Git commands, commits or pushes performed.

## Audit recorded before implementation

- Directory: Employee.Read route/feature gate, user-scoped session/cache infrastructure, server search and department/designation/employment-status/record-active filters, URL page state, fixed 20-row pagination. Backend ordering is EmployeeNumber then EmployeeId; no interactive sort exists. Filters reset page and notice. Search submits trimmed text, not each keystroke.
- Employee identification: existing name, employee number, department/designation, current employment status and separate Active/Inactive employee record. These are distinct domain facts.
- Quick view: existing employee detail query in a Radix Sheet, current employment/contact information, link to Employee 360; dismissal restores focus to the triggering row action without clearing filters.
- Employee 360: identity/action header; Overview, Account access, Personal & contacts, Employment history and conditional Teacher profile. Existing tabs mount content on selection. Detail, master-data and employment-history query behavior is preserved.
- Full-page create/edit and employment change/end/rehire workflows use real APIs, existing validators, CSRF client, pending protection, server validation, explicit confirmations and unsaved-navigation blocking. These are dense domain workflows and will remain full pages rather than being forced into modals.
- Account access: limited readiness information for employee readers; privileged account details/actions require Security.Manage. Linked-account state is distinct from employee/employment/credential state. No authorization broadening is proposed.
- Existing loading/empty/error/401/403/conflict states and targeted retries remain authoritative. No new data source or business metric is proposed.

Presentation issues: the search row consumes a separate wide line; controls and surrounding blocks have accumulated gaps; the create action reads like secondary text; auto-fit facts can become an overly wide wall of fields; profile actions compete at equal weight; profile tabs wrap unpredictably; section padding compounds with parent spacing; the quick-view body duplicates identity context without a stable navigation footer. Raw unresolved master GUIDs are a fallback for missing references, not a new field to invent or silently resolve.

## Revised information architecture

Directory: one shell-owned title, clear create action, compact search/filter surface, server total, semantic table, pagination, contextual inspection drawer. Employee 360: identity and separate record/employment state, primary edit action with quieter lifecycle links, horizontally contained supported tabs and bounded information groups. Full-page forms retain their field/validation/lifecycle semantics with consistent section spacing and action footer presentation.

## Implementation

- Directory: existing create link uses the shared primary-button treatment and a 16px Plus icon. Search and filters share a named, bordered surface. At 1280px and above they share one row; narrower widths progressively wrap. Existing server total and pagination remain unchanged. Record status uses a neutral badge, separate from employment status. Quick view has an Eye icon and the approved 480px drawer size.
- Employee 360: restrained identity surface with actual-name initials, employee number, separate record/employment statuses and existing permitted actions. Initials are decorative to assistive technology. Edit is visually primary among profile actions; employment-change/end/rehire links retain their existing gates and destinations.
- Supported tabs use the shared scroll overflow option instead of wrapping. Overview groups existing facts into Employment information and Dates & reporting. Facts use three columns on desktop and two on narrower screens, with a two-column override inside the inspection drawer.
- Forms: retain dense full-page workflows. Shared employee section/grid spacing is reduced using existing spacing tokens. Create/edit Save and Cancel use a stable sticky action region; no submission, validation or navigation-blocking code changed.
- Reuse: existing Button, Badge, Avatar, Tabs, Sheet, Table, Pagination, FormField, Input, Select, AlertDialog and QueryState; approved semantic color/spacing/density/radius tokens and Lucide icons. No dependencies or competing primitives added.
- Drawer content and navigation semantics were retained. No new drawer footer, data source, unsupported tab, account action or sorting control was invented.

## Contract and security preservation

Directory still uses GET /api/employees with pageSize=20 and existing URL-backed search, department, designation, employment-status and record-active filters. Server ordering remains EmployeeNumber then EmployeeId. Detail, employment-history, master-data and account lifecycle queries and their permission gates are unchanged. Create/edit/lifecycle API payloads and handlers remain unchanged.

Employee.Read remains the read boundary; Employee.Manage remains the mutation boundary; Security.Manage remains the privileged account-action boundary. Existing validation, CSRF, session cache isolation, 401/403 handling, conflict handling and targeted retry behavior remain intact. No sensitive permission was expanded.

SHA-256 comparison of all 427 frontend/src and backend src files captured before implementation identified only the six source files listed below as changed. This proves authentication, shell, HR Dashboard, account-access implementation, backend and migration source preservation within that inventory. No database commands or migrations were executed, and no QA account or operational record was modified. Browser verification did not submit mutation forms.

## Known limitations and V3.6 recommendations

- Product-owner visual approval remains required. Automated and browser checks do not approve the design.
- Only Chromium was inspected. A full screen-reader and Firefox/WebKit pass remains a useful later verification step.
- Live mutation, multi-page data and unauthorized-persona scenarios were deliberately not fabricated. Their coverage is isolated fixture testing, not a claim of six-persona live authorization verification.
- Long native-select values may truncate at intermediate desktop widths; the opened native select retains full labels. Mobile filters remain stacked and can require scrolling before reaching the table.
- Existing unresolved-reference GUID fallbacks, purposefully displayed account-provisioning identifiers and existing supported tab scope remain unchanged.
- Future V3.6 should modernize only its approved workflow using these established density, information-grouping and action conventions; separately consider real-data multi-page usability and cross-browser/assistive-technology review. No V3.6 implementation or deferred browser-tab persistence was started.
