# F3.5 — Premium Authentication Experience

Historical experiment: this presentation was superseded by [V2.2](V2.2-PREMIUM-AUTHENTICATION.md). The report is retained as history; V2.1 is the current visual authority.

## Composition and visual direction

Retained the centered campus composition: the existing front-facing school image provides recognizable institutional identity, while one compact, opaque card gives all authentication tasks a stable reading surface. A split layout would reduce the visible campus and require additional mobile recomposition without improving these short forms.

The same real crest, school/system names, restrained gold accent, warm surface, burgundy actions and modest shadow now appear across login, activation, recovery, reset and their existing status states. The campus uses natural cover positioning with a 14% navy overlay (18% on mobile), without blur, stretching or artificial scaling. No assets, packages or brand tokens were changed.

## Reusable presentation and UX

- `AuthLayout` shares the panel and branding across authentication routes.
- `AuthBrand`, `AuthHeader` and `AuthStatus` provide consistent identity, task hierarchy and feedback.
- Auth styles remain scoped; F1 components and F2/F4 layouts are preserved.
- Maximum card width is 432px, with 32px horizontal/28px vertical desktop padding and 24px mobile padding. Cards grow naturally for validation; no fixed height or reserved error area.
- Existing shared 14px labels, 8px label/control spacing and 6px error spacing remain. Auth controls are 48px high with 16px text; the inline password toggle has a 44px target and does not move when toggled.
- Blue focus indicators remain distinct from red validation borders. Existing autocomplete contracts remain, with scoped autofill styling and reduced-motion support.
- Field errors stay next to controls; form errors use compact announced alerts. Neutral recovery success retains enumeration-safe wording and the existing sign-in next action.
- Task headings/wrappers do not receive programmatic focus. Existing login Username focus remains. Password toggle names/pressed state, labels, error associations, logical tab order and loading announcements are preserved; submit also exposes `aria-busy`.
- Public activation links and Remember Me were not added.

## Authentication/security preservation

No changes to API payloads/endpoints, session provider, session bootstrap, CSRF, cookies, central 401/cache handling, route guards, capabilities, activation/reset credentials or password requirements. All request, validation and session handlers in `AuthForm` retain their existing logic.

The API was restarted afterward.

The supported temporary `f4-review` and `f4-bootstrap-helper` accounts remain unchanged. ### Rendered browser verification

Chromium in-app browser inspected login, activation, forgot-password and reset forms at **1440×900, 1280×800, 1024×768, 768×1024, 430×932 and 390×844**. All normal forms fit without horizontal overflow or unnecessary vertical scrolling. Login card height was approximately 587px desktop/571px mobile; activation/reset approximately 628px desktop/612px mobile. A shortened 390×500 viewport permits natural vertical scrolling while retaining usable fields and no horizontal overflow; this is a viewport simulation, not a physical mobile-keyboard test.

Direct login/refresh, Username and Password focus, populated fields, empty and one-field validation, password visibility and keyboard navigation were inspected. Network-error presentation was verified against the genuinely offline API. Recovery neutral success was inspected using a reserved unknown address; it created no account or recovery fixture. Missing activation/reset links show the existing unavailable-link guidance. Valid-shaped synthetic links were used only to inspect password forms, never to submit or alter credentials.

Authenticated login/logout, rejected credentials, in-flight submission, activation/reset success and invalid/expired-token responses are covered by automated tests; they were not repeated with real credentials in this browser pass. Actual password-manager/browser autofill was not reproducible; autocomplete and autofill CSS were reviewed. Firefox/WebKit were unavailable, and no Safari testing is claimed.
