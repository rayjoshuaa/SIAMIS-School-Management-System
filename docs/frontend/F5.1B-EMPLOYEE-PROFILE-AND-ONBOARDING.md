# F5.1B — Employee profile and onboarding improvements

Status: implemented and verified; awaiting product-owner review. F5.1C has not started.

## Implementation

- Registration retains automatic permanent numbering and the existing atomic Employee + initial EmploymentRecord workflow. Personal details, optional initial contact information, and employment details have separate sections. Initial work email/mobile use the existing nested contact contract in the same registration POST. The success notice displays the actual generated number. Account provisioning remains a separate Security.Manage workflow.
- Employee 360 retains Overview, Account access, Personal & contacts, Employment history, and existing lifecycle actions. Personal details now identify the permanent number explicitly. Contact information, addresses, and emergency contacts have readable sections with capability-gated Add/Edit actions.
- Supporting editors reuse V3 FormField/Input/Button and the shared 560px Dialog. Required fields, email validation, backend field errors, pending submission, dirty-close confirmation, before-unload protection, and opener focus restoration are supported. Address options come from existing master-data APIs, including existing inactive values.
- Profile editing retains employment context and supporting collections. Numbers cannot be edited. No employee deletion or supporting-record deletion UI was added.
- Fixed an additive DTO gap: the profile emergency-contact response now includes existing stored AlternativePhone and Address. Legacy Mobile/Email fields remain readable and are not overwritten by the dedicated emergency-contact editor.

## Existing API contracts used

- GET/POST `/api/employees`; GET/PUT `/api/employees/{employeeId}`.
- GET/POST `/api/employees/{employeeId}/contacts`, `/addresses`, `/emergency-contacts`.
- PUT corresponding child routes ending in `/{childId}`; server validates child ownership.
- GET `/api/master-data/address-types?includeInactive=true` and `/api/master-data/countries?includeInactive=true`.
- Employment lifecycle and account-provisioning endpoints are unchanged. No new endpoint was introduced.

## Product-owner correction — automatic initial employment status

Registration no longer displays or validates an Employment Status selector. The create contract no longer defines EmploymentStatusId. Its existing extension-data validation rejects explicitly supplied employmentStatusId keys (including null/case-insensitive names) with HTTP 400; clients must omit the field. Update contracts and authorized employment lifecycle operations retain their existing status fields and rules.

Inside the existing Serializable registration transaction, the service resolves the canonical seeded `ES-001` Active master record, requiring its Active name, enabled flag and non-terminal classification. If unavailable, registration fails with a configuration conflict rather than choosing another status or consuming an employee number. No master records or history are changed.

Future hire behavior remains effective-dated: coverage starts at StartDate or, if omitted, HireDate. An open/latest record marked IsCurrent with stored Active status is not proof of current work. Employee 360 now distinguishes a future effective start with `Scheduled to start {date}` and labels the stored value as Employment record status. This presentation uses the existing UTC calendar-day convention; no employment, attendance or payroll date rules were altered. Employee record activation and account activation remain separate concepts.
