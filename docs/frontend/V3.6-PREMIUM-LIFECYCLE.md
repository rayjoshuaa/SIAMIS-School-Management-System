# SIAMIS V3.6 — Employment and account lifecycle

Status: **V3.6 PREMIUM EMPLOYMENT & ACCOUNT LIFECYCLE READY FOR PRODUCT-OWNER REVIEW**. Not committed or pushed. Product-owner visual approval pending.

Subsequent product-owner cross-workspace refinement is documented in [V3.6-CROSS-WORKSPACE-CONSISTENCY.md](V3.6-CROSS-WORKSPACE-CONSISTENCY.md). The implementation and screenshots below record the initial V3.6 presentation before that refinement.

## Audit recorded before implementation

- Employment change, end and rehire are full-page Employee.Manage workflows. Effective-date/status filtering, current-record checks, linked-account offboarding decisions, concurrency identifiers, CSRF requests, validation and unsaved-navigation blocking already exist. End employment requires explicit confirmation; rehire does not automatically enable an account.
- Employee 360 history reads existing records, preserving API order and date values; current/historical status is currently plain text. Account access reads the limited account-lifecycle contract; Security.Manage alone permits privileged account details/status/complete role replacement. Unknown roles and changed linkage fail safely.
- User Accounts requires Security.Manage in routing and the component. Bounded account list/detail, passwordless provisioning with five existing role choices and optional validated Employee GUID, activation/recovery issuance and Development-only transient delivery collection already exist. No passwords are chosen by administrators. There is no capability editor, unlink/relink UI, unlock command or account deletion UI to invent.
- Account creation is a focused dialog, inspection a drawer, credential issuance a replacement confirmation (not nested). Pending dismissal and opener focus restoration exist. Create dismissal currently does not protect unsaved input. Linked-account role replacement uses the existing consequential confirmation. Existing status/version/session revocation/last-usable-admin protection remain backend responsibilities.
- Presentation weaknesses: repeated account-status facts, ungrouped security facts, competing action hierarchy, technical identity vocabulary, generic lifecycle help text, indistinct historical records, bare role lists, legacy overlay widths and table density. Success/error messages exist and must remain honest.

## Revised information architecture

Employment: current context and explicit operation consequences above unchanged fields; readable preserved dates/history and clear current/historical markers. Account access: employment context, separate linked-account identity/access and credential/verification groups, then deliberate administration actions. User Accounts: compact real account list, bounded create modal, grouped inspection drawer and unchanged credential confirmations. No new business workflows or data fetching.

## Implementation

- Employment change, end and rehire pages show the employee and existing employment context before the form. Explanations describe existing effective-date, history and linked-account consequences. The end-status label is now “End-of-employment status”. Validation, payloads, confirmations and transition rules are preserved.
- Employment history uses clear Current/Historical badges and a concise explanation of recorded dates. Ordering and date values remain unchanged.
- Employee 360 separates employment context, linked account identity/access, credentials/verification and account administration. Real assigned roles use shared neutral badges. Redundant status facts were removed without conflating employment, account access, password readiness or lockout.
- User Accounts uses compact spacing and a contained scrolling table. Account creation uses the existing 560px modal preset; inspection uses the existing 480px drawer preset. Mobile uses the existing responsive overlay behavior.
- Account creation now uses the shared dirty-form dismissal protection. Cancel, Escape and backdrop dismissal follow the same protection; pending submission prevents dismissal. Credential confirmations replace the drawer rather than nesting overlays.
- Linked employee navigation is visible only with the existing Employee.Read capability. Security.Manage still governs account administration. No role-name authorization, new capabilities or role grants were added.
- Presentation uses approved semantic tokens, shared controls, badges, facts, overlays and restrained 16px Lucide icons. Existing success, validation, loading, empty and error behavior remains intact.

## Existing contracts preserved

| Workflow                  | Existing API contract                                 | Authorization and behavior                                                    |
| ------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| Employment history        | GET `/api/employees/{employeeId}/employment-history`  | Existing Employee.Read; recorded history retained                             |
| Limited account lifecycle | GET `/api/employees/{employeeId}/account-lifecycle`   | Existing safe HR account context                                              |
| Employment change         | POST `/api/employees/{employeeId}/employment-changes` | Existing Employee.Manage; new effective record and previous end date rules    |
| End employment            | POST `/api/employees/{employeeId}/end-employment`     | Existing permissions, explicit account decision, concurrency and confirmation |
| Rehire                    | POST `/api/employees/{employeeId}/rehire`             | Existing non-overlap/history rules; does not automatically reactivate account |
| Account list/detail       | GET `/api/admin/users`, GET `/api/admin/users/{id}`   | Security.Manage; bounded list and existing detail restrictions                |
| Account provisioning      | POST `/api/admin/users`                               | Passwordless provisioning, existing roles and optional Employee link          |
| Account access change     | PATCH `/api/admin/users/{id}/status`                  | Existing linked-account controls, version protection and session revocation   |
| Role replacement          | PUT `/api/admin/users/{id}/roles`                     | Existing complete role set replacement and security protections               |
| Activation/recovery       | POST `/api/admin/users/{id}/issue-credentials`        | Existing eligibility and delivery rules; no new token exposure                |

Standalone User Accounts supports the existing create/read/activation/recovery UI. Account enable/disable and role replacement remain in the linked Employee 360 account administration interface. No capability editor, unlink/relink, account deletion or unsupported unlock action was introduced. Production credential delivery and Development-only transient collection remain unchanged.

## Limitations and V3.7 recommendations

- Product-owner visual approval remains pending; technical browser review does not grant approval.
- Live review did not exercise consequential writes, every persona or a rehire-eligible employee. Regression fixtures cover those contracts; an operator-approved mutation checkpoint can verify them separately.
- Chromium was inspected; no Firefox/WebKit verification is claimed. Keyboard/focus checks were performed, but no full assistive-technology certification is claimed.
- Browser-tab state reset remains deferred and was not changed.
- Full-page screenshots can show sticky header/footer capture artifacts. Viewport captures are included for account inspection and lists.
- For V3.7, use the same context → form → explicit consequence → confirmation pattern in the separately approved next workflow. Preserve capability-specific visibility and independent employment/account state. Do not infer permission from role labels or broaden this checkpoint into new account operations.
