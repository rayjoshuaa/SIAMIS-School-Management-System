# F5.1D — Controlled employee deletion

Date: 2026-10-09. Status: implementation verified; awaiting product-owner review. No Git commands, commits or pushes performed.

## Scope and authorization

End Employment remains the normal departure workflow, preserving identity, history and rehire. There is no new deactivation workflow. Exceptional permanent deletion is restricted to erroneous registrations.

`Employee.DeletePermanent` is a new explicit capability granted only to SystemAdmin by default. Existing grants are retained. HRAdmin, PayrollAdmin, Management and Employee do not receive it. Employee.Manage alone is insufficient. Assessment and deletion also require Employee.Read and an authenticated actor at the application-service boundary. There is no SystemAdmin bypass and no confidential document grant.

Endpoints:

- `GET /api/employees/{id}/permanent-deletion`: no-store dependency assessment, state, opaque version and safe blocker codes.
- `POST /api/employees/{id}/permanent-deletion`: exact employee number, reason (5–120 characters) and current assessment version; success is 204.

Real Identity/session authorization and existing CSRF protection remain active. Unexpected JSON properties are rejected. No account unlinking, password changes or automatic employee/account deletion are included.

## Eligibility and provenance

Eligible records must have intact identity triggers and a matching assigned, non-retired permanent reservation; an active employee record; exactly one current, open initial employment record; and authenticated creation evidence for both Employee and EmploymentRecord with the new employee-ownership audit marker.

All existing Development employees predate that marker and remain ineligible. No provenance is fabricated or backfilled. Employment changes, retained protected audit history, legacy photo references, unrecognized employee audit history, inconsistent identity protection and unknown dependency schemas fail closed. No statutory retention period or legal-hold clearance is inferred from the absence of a separate retention model.

The engine checks the actual SQL foreign-key catalog, including disabled/untrusted constraints and cascade behavior. The known 31 direct Employee foreign-key references cover:

- Attendance, events, review actions/cases, clock sessions and finalized revisions.
- Leave, entitlements, calendars, compensation, payroll assignments/results, PIT payment schedules, statutory enrollment and tax records.
- Contracts, documents, verifier references, photo revisions including removal tombstones, employee history and performance/reviewer references.
- Teacher profiles, employment/manager references and linked Users, including disabled accounts.
- The four permitted registration-child categories: initial employment, contacts, addresses and emergency contacts.

Any protected root blocks deletion, preserving its indirect child histories. Non-FK `PayrollRuleTargets` Employee references are checked separately. Unknown catalog references block even when empty. The implementation does not invent future academic or timesheet models.

Document and other protected blockers are generic; assessment does not return confidential metadata, storage keys or paths. The payroll-target-specific code is returned only with Payroll.Read; otherwise the generic protected-record code is used.

## Transaction, concurrency and audit

Assessment and deletion use serializable transactions. The Employee row is locked with XLOCK/HOLDLOCK; reference queries take UPDLOCK/HOLDLOCK range locks. Deletion repeats every check under the transaction and compares the deterministic preview fingerprint, including permitted child values. A preview alone never authorizes deletion.

Existing FK writers remain protected by SQL referential locking and NO_ACTION constraints. PayrollRuleTarget create/update now hold a serializable transaction and lock an Employee target through the existing employment-integrity helper, covering that non-FK write path. Payroll formulas and calculations are unchanged.

Only the eligible initial employment record and ordinary contacts/addresses/emergency contacts are explicitly removed with the Employee. Permanent number/GUID reservations remain; the existing trigger retires the reservation atomically. No cascading historical deletion or physical file purge occurs.

The existing immutable security-audit system is reused. Generic entity audits now retain Employee ownership, including an old Employee target when a payroll reference moves, so future removed histories remain detectable. POST attempts are audited before authorization/CSRF/model validation; authenticated capability denials receive an additional denial event. Service denials/failures are recorded outside the rolled-back mutation transaction; success evidence commits atomically with deletion. CSRF/model rejection has attempt evidence plus the normal HTTP response/log, rather than a separate service outcome event. Audit persistence failure fails closed.

The existing shared Dialog, Button, Input, FormField and query/API infrastructure are reused. Safe blocker explanations disable deletion. Eligible confirmation requires a reason and exact employee number; stale/conflicting results retain feedback and refresh assessment. Dirty/pending protections, loading feedback, keyboard focus containment and Escape/focus return are preserved. ## Housekeeping and limitations

The two `.artifacts/f51c-deployment-audit/` source utilities are temporary deployment tools. Existing backup and verification evidence remain recorded in the F5.1C deployment baseline/logs. The utilities are retained unchanged through this review; no automatic cleanup was performed.

Legacy employees deliberately remain blocked. Future schema additions require updating/reviewing the dependency contract; unknown FKs block automatically, but future non-FK references must be explicitly integrated. Arbitrary database-owner/raw SQL writes lie outside application audit guarantees. Locking may serialize concurrent writers, and transient conflicts require a fresh assessment. No retention-period waiver, account unlinking, file purge or deletion of records with protected history is provided.
